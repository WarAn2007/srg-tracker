# Как была создана первая версия SRG-Tracker

Дата работы: 27 июля 2026 года.

Этот файл — не только список команд. Его цель — объяснить логику проекта так, чтобы в будущем можно было самостоятельно создать похожую ML-модель без помощи ИИ.

## 1. Что мы строили

Одна строка данных описывает состояние одного студента по одному курсу в конце определённой недели:

```text
student_id + course_id + semester + week
```

По этой строке решаются три отдельные задачи:

1. Регрессия: предсказать `final_course_score`.
2. Бинарная классификация: предсказать `course_outcome` (`pass` или `enroll`).
3. Многоклассовая классификация: предсказать `learning_pace` (`behind`, `on_track`, `ahead`).

Это три разных модели. Регрессия возвращает число, а классификаторы — классы и, где возможно, вероятности.

## 2. Почему данные разделены на train, validation и test

- `train.csv` используется для обучения кандидатов.
- `validation.csv` используется для сравнения алгоритмов и выбора лучшего.
- `test.csv` используется один раз после завершения выбора.

Разделение выполнено по `student_id`. Если один и тот же студент попадёт и в train, и в test, модель может частично запомнить его поведение. Метрика окажется лучше, чем реальная способность работать с новым студентом. Поэтому студенты во всех трёх split различаются.

В проекте:

```text
train:      300 студентов / 42 000 строк
validation: 100 студентов / 14 000 строк
test:        50 студентов / 7 000 строк
```

## 3. Что такое leakage и как мы его предотвратили

Data leakage — это попадание в признаки информации, которой ещё нет в момент прогноза.

Например, нельзя прогнозировать итоговый балл, используя `final_exam_score_audit_only`: финальный экзамен происходит в будущем и почти напрямую определяет итоговый балл. Нельзя передавать самой модели и правильный ответ `final_course_score`.

В `src/config.py` создан точный список допустимых `FEATURE_COLUMNS`. `src/preprocessing.py` выбирает только эти колонки. Поэтому случайная дополнительная колонка из CSV не попадёт в обучение.

`student_id` также исключён. Он нужен для разделения данных и анализа, но не должен быть учебным признаком.

## 4. Что находится в каждом файле `src`

### `src/config.py`

Хранит настройки, которые используются в разных частях проекта:

- пути к данным, моделям и отчётам;
- `RANDOM_STATE` для воспроизводимости;
- названия трёх target;
- список разрешённых признаков;
- список числовых и категориальных признаков;
- имена сохраняемых моделей.

Такой файл предотвращает ситуацию, когда один и тот же список признаков по-разному записан в нескольких ноутбуках.

### `src/generate_dataset.py`

Создаёт синтетические записи и сохраняет `train.csv`, `validation.csv`, `test.csv`. Для генерации используются NumPy и pandas.

NumPy отвечает за случайные числа и математические вычисления. Фиксированный seed `20260726` означает, что повторный запуск создаёт те же данные. pandas собирает записи в таблицу `DataFrame` и сохраняет CSV.

### `src/preprocessing.py`

Загружает CSV и превращает сырые колонки в форму, пригодную для scikit-learn.

Использованные компоненты:

- `SimpleImputer(strategy="median")` заменяет пропущенные числовые значения медианой, вычисленной только по обучающим данным;
- `SimpleImputer(strategy="most_frequent")` обрабатывает пропуски категорий;
- `OneHotEncoder(handle_unknown="ignore")` превращает `course_id` в числовые индикаторы;
- `StandardScaler` масштабирует числа для Ridge и Logistic Regression;
- `ColumnTransformer` применяет разные преобразования к числовым и категориальным колонкам;
- `Pipeline` связывает preprocessing и модель.

Пропуски в ранних неделях нормальны: например, до первой контрольной ещё нет средней оценки за неё, а до midterm нет midterm-балла.

### `src/train.py`

Обучает несколько кандидатов для каждой задачи.

Для итогового балла:

- `DummyRegressor` — baseline, всегда предсказывающий среднее;
- `Ridge` — линейная регрессия с регуляризацией;
- `RandomForestRegressor` — ансамбль деревьев;
- `HistGradientBoostingRegressor` — последовательное исправление ошибок деревьями.

Для классификаций:

- `DummyClassifier` — baseline, всегда выбирающий наиболее частый класс;
- `LogisticRegression` — линейный вероятностный классификатор;
- `RandomForestClassifier`;
- `HistGradientBoostingClassifier`.

Baseline необходим, чтобы доказать, что ML-модель действительно полезнее простого ответа.

Кандидаты учатся на train и сравниваются на validation. Критерии выбора:

- score: минимальный RMSE;
- outcome: максимальный F1 для класса `enroll`;
- pace: максимальный Macro-F1.

После выбора победитель заново обучается на объединённых train + validation. Это допустимо, потому что выбор уже завершён, а test всё ещё не использован.

### `src/evaluation.py`

Содержит функции метрик.

Для регрессии:

- MAE — средняя абсолютная ошибка в баллах; проще всего объяснить человеку;
- RMSE — сильнее штрафует большие ошибки;
- R² — доля объяснённой изменчивости цели.

Для `course_outcome`:

- Recall `enroll` — какую долю реально нуждающихся в повторном прохождении нашли;
- F1 `enroll` — баланс precision и recall;
- ROC-AUC — качество ранжирования по вероятности риска;
- accuracy — общая доля правильных ответов.

Для `learning_pace`:

- Macro-F1 — одинаково учитывает каждый класс;
- balanced accuracy — средний recall по классам;
- accuracy — общая правильность.

### `src/eda.py`

Выполняет exploratory data analysis:

- считает размеры данных;
- проверяет пересечение студентов;
- считает доли пропусков;
- создаёт распределения targets;
- показывает средние показатели по неделям.

Таблицы сохраняются в `reports/metrics`, графики — в `reports/figures`.

### `src/final_evaluation.py`

Загружает уже выбранные модели и один раз оценивает их на test.

Кроме общей метрики, файл сохраняет:

- отдельный прогноз каждой test-строки;
- ошибки по неделям;
- ошибки по курсам;
- confusion matrix для классификации;
- график actual versus predicted для итогового балла.

Это называется error analysis. Общая метрика не показывает, где именно модель работает хуже.

### `src/inference.py`

Используется после обучения:

1. Проверяет, что пользователь передал все 12 признаков.
2. Отклоняет targets и неизвестные поля.
3. Загружает три `.joblib`-файла.
4. Возвращает итоговый балл, outcome, вероятность `enroll`, pace и предупреждение.

`joblib.dump()` сохраняет обученный scikit-learn Pipeline. `joblib.load()` загружает его. Сохраняется весь Pipeline, а не только последний алгоритм, поэтому новый record проходит точно такую же обработку пропусков и категорий, как train.

### `src/utils.py`

Содержит маленькие общие функции: создание каталогов и сохранение JSON. Основная ML-логика сюда не помещается, иначе `utils.py` превратится в непонятный набор несвязанных функций.

### `src/__init__.py`

Делает `src` Python-пакетом. Благодаря этому можно запускать:

```powershell
python -m src.train
```

и использовать импорты вида:

```python
from src.preprocessing import load_split
```

## 5. Что находится в ноутбуках

- `01_eda.ipynb` — знакомство с данными и проверки split.
- `02_baselines.ipynb` — таблица сравнения моделей и выбранные победители.
- `03_demo.ipynb` — пример одного прогноза.
- `04_final_evaluation.ipynb` — финальные test-метрики и error analysis.

Ноутбуки тонкие: основная логика находится в `src`. Это важно для повторного использования, тестирования и предотвращения копирования слегка различающегося кода.

## 6. Что получилось

На validation для всех задач победил HistGradientBoosting.

Финальные test-результаты:

| Задача | Результат |
| --- | --- |
| Итоговый балл | MAE 3.18, RMSE 4.26, R² 0.815 |
| Course outcome | Recall enroll 0.720, F1 enroll 0.759, ROC-AUC 0.941 |
| Learning pace | Macro-F1 0.855, balanced accuracy 0.851 |

Интерпретация MAE 3.18: в среднем прогноз итогового балла отличается от синтетической истины примерно на 3.18 балла.

Score MAE по неделям уменьшается примерно с 6.00 на первой неделе до 2.08 на четырнадцатой. Это ожидаемо: ближе к концу курса известно больше оценок, заданий и результатов midterm.

Recall `enroll` 0.720 означает, что модель находит около 72% test-примеров класса `enroll`. Для реальной early-warning системы этого может быть недостаточно. Можно выбрать другой порог вероятности и повысить recall ценой большего количества ложных предупреждений.

## 7. Автоматические тесты

`tests/test_pipeline.py` проверяет:

- отсутствие leakage-полей среди признаков;
- отсутствие пересечения студентов;
- отказ при неполном record;
- отказ при передаче target;
- возможность трёх сохранённых моделей выполнить прогноз.

Использован встроенный модуль `unittest`, поэтому дополнительная тестовая библиотека не нужна.

## 8. Как полностью повторить работу

Откройте PowerShell в корне проекта:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
python src/generate_dataset.py
python -m src.eda
python -m src.train
python -m src.final_evaluation
python -m unittest discover -s tests -v
jupyter notebook
```

Порядок имеет значение:

1. Генератор создаёт данные.
2. EDA проверяет данные.
3. Train выбирает и сохраняет модели.
4. Final evaluation использует сохранённые модели.
5. Tests проверяют безопасность и работоспособность.
6. Demo использует готовые `.joblib`.

## 9. Как создать похожий проект с другими данными

1. Чётко определите одну строку данных и момент прогноза.
2. Определите targets и признаки, реально доступные в этот момент.
3. Найдите все возможные leakage-поля.
4. Выберите правильную единицу разделения данных: пользователь, пациент, устройство или временной период.
5. Создайте простой baseline.
6. Обучите минимум два осмысленных кандидата.
7. Выберите метрику, связанную с ценой ошибки.
8. Используйте validation для выбора, test — только для финального отчёта.
9. Изучите ошибки по важным группам и времени.
10. Сохраните preprocessing вместе с моделью в Pipeline.
11. Добавьте проверку входа, тесты, документацию и ограничения.

## 10. Ограничения этой версии

- Данные синтетические и созданы по заданным правилам.
- Высокая метрика не доказывает работу на реальных студентах.
- `learning_pace` также является синтетической меткой.
- Нет demographic features, поэтому нельзя делать выводы о fairness для реальных групп.
- Модель не устанавливает причинность: плохая посещаемость может быть связана с риском, но прогноз не доказывает причину.
- Прогноз нельзя превращать в автоматическое решение об оценке или зачислении.

Следующее возможное улучшение — подобрать threshold для `enroll` на validation в соответствии с требуемым recall, не прикасаясь повторно к test, а затем проверить подход на новом полностью независимом наборе данных.
